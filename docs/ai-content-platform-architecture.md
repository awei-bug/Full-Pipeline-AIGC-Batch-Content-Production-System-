# AI内容创作平台整体架构说明

## 1. 文档目的

本文档用于说明 AI 内容创作平台的整体架构设计。平台的目标是让用户通过输入提示词，生成对应的图片或视频，并支持任务管理、结果存储、内容审核、计费运营和后续扩展。

本文档聚焦以下内容：

- 业务目标与建设范围
- 平台整体架构
- 核心服务职责划分
- 图片与视频生成主流程
- 数据存储与系统集成设计
- 部署与网络分区建议
- 安全、性能与可运维要求
- 分阶段建设建议

## 2. 建设目标

### 2.1 平台目标

建设一个统一的 AI 内容创作平台，面向终端用户或企业客户提供以下能力：

- 输入文本提示词生成图片
- 输入文本提示词生成视频
- 上传参考图进行图生图或图生视频
- 对生成结果进行预览、下载、再编辑和发布
- 支持会员、积分或额度消耗机制
- 支持平台级内容安全审核与运营管理

### 2.2 核心设计原则

- 统一入口：图片和视频能力通过统一创作入口访问
- 异步生成：所有高耗时生成任务采用异步编排
- 能力解耦：前台业务、模型编排、推理执行、媒体处理分层设计
- 易扩展：后续可引入更多模型、模板、风格和业务场景
- 可运营：从第一阶段开始考虑计费、审核、监控和成本控制

## 3. 业务范围

### 3.1 用户侧能力

- 用户注册、登录、权限控制
- 提示词输入与参数配置
- 图片生成、视频生成
- 历史作品管理
- 参考素材上传
- 作品下载、分享、删除、再次生成

### 3.2 平台侧能力

- Prompt 处理与增强
- 模型路由与任务编排
- 内容审核
- 后处理与转码
- 媒体资产存储
- 套餐、积分、额度管理
- 运营后台管理

## 4. 整体架构概览

平台采用分层架构，整体可分为接入层、业务服务层、AI 编排层、推理执行层和数据支撑层。

```text
[Web/H5/App]
    |
    v
[CDN/WAF]
    |
    v
[API Gateway]
    |
    +-------------------+-------------------+-------------------+
    |                   |                   |                   |
    v                   v                   v                   v
[认证服务]          [用户/订阅服务]     [内容创作服务]       [管理后台]
                                            |
                                            v
                                     [Prompt处理服务]
                                            |
                                            v
                                     [审核/策略服务]
                                            |
                                            v
                                     [任务编排服务]
                                            |
                    +-----------------------+------------------------+
                    |                                                |
                    v                                                v
             [图片生成引擎]                                     [视频生成引擎]
                    |                                                |
                    +-----------------------+------------------------+
                                            |
                                            v
                                       [后处理服务]
                                            |
                                            v
                                   [对象存储/媒体资产库]
                                            |
                                            v
                              [结果查询 / 下载 / 分享 / 再编辑]
```

## 5. 分层架构说明

### 5.1 接入层

接入层负责所有外部访问流量接入与基础安全控制。

主要组件：

- Web 前端
- H5 或移动端应用
- CDN
- WAF
- API Gateway

核心职责：

- 提供统一 API 入口
- 进行鉴权、限流、路由和访问审计
- 加速静态资源和媒体资源分发
- 拦截恶意请求和常见攻击

### 5.2 业务服务层

业务服务层承接用户操作和平台运营能力，负责创作业务的业务逻辑处理。

建议拆分以下服务：

#### 5.2.1 认证服务

- 用户注册、登录、登出
- Token 管理
- 第三方登录或企业 SSO 对接

#### 5.2.2 用户与订阅服务

- 用户资料管理
- 套餐管理
- 积分、额度、会员权益
- 消费记录与账单

#### 5.2.3 内容创作服务

- 接收生成图片和生成视频请求
- 处理前端提交参数
- 校验用户权限、余额和配额
- 创建创作任务并返回任务编号

#### 5.2.4 作品管理服务

- 作品列表、详情、版本记录
- 收藏、删除、归档
- 下载和分享链接管理

#### 5.2.5 素材管理服务

- 上传参考图、品牌素材、模板素材
- 维护素材元数据
- 为后续图生图和图生视频提供输入

#### 5.2.6 管理后台服务

- 用户管理
- 模板管理
- 内容审核管理
- 运营数据统计
- 模型与策略配置

### 5.3 AI 编排层

AI 编排层是平台的核心中台，负责将用户创作请求转换成可执行的模型任务。

#### 5.3.1 Prompt 处理服务

主要职责：

- 清洗用户输入
- 补全系统提示模板
- 组装负面提示词
- 对风格、尺寸、时长、帧率等参数标准化
- 进行多语言兼容

该层的目标不是直接生成内容，而是把输入转成结构化、可复用、可审计的生成请求。

#### 5.3.2 审核与策略服务

主要职责：

- 提示词合规校验
- 敏感主题检测
- 黑白名单控制
- 根据用户等级、套餐、场景控制可调用模型范围

该服务应在任务真正进入推理流程前执行，避免无效 GPU 消耗。

#### 5.3.3 模型路由服务

主要职责：

- 根据任务类型选择图片模型或视频模型
- 根据分辨率、时长、风格要求选择具体模型版本
- 根据成功率、时延、成本做动态路由
- 支持灰度发布和 A/B Test

#### 5.3.4 任务编排服务

主要职责：

- 生成任务单
- 维护任务状态机
- 推送任务到消息队列
- 执行超时、重试和失败补偿
- 接收模型回调和状态更新

建议任务状态至少包括：

- `created`
- `queued`
- `running`
- `post_processing`
- `success`
- `failed`
- `cancelled`

### 5.4 推理执行层

推理执行层负责真正执行图片或视频生成，是平台算力消耗最大的部分。

#### 5.4.1 图片生成引擎

支持能力建议包括：

- 文生图
- 图生图
- 局部重绘
- 风格迁移
- 高清修复

#### 5.4.2 视频生成引擎

支持能力建议包括：

- 文生视频
- 图生视频
- 首尾帧控制
- 镜头运动控制
- 分镜片段生成与拼接

#### 5.4.3 后处理服务

主要职责：

- 图片超分
- 去噪和修复
- 视频转码
- 视频封面和缩略图生成
- 水印处理
- 统一输出格式转换

### 5.5 数据支撑层

数据支撑层提供结构化数据、缓存、异步消息、媒体文件和观测数据的统一存储能力。

建议组件如下：

- PostgreSQL：用户、任务、订单、作品元数据
- Redis：缓存、会话、分布式锁、限流
- 消息队列：异步任务解耦与削峰
- 对象存储：图片、视频、缩略图、原始素材
- 日志平台：应用日志、审计日志
- 监控平台：指标、告警、链路追踪
- 向量库（可选）：用于素材检索、风格推荐、提示词相似度分析

## 6. 核心业务流程

### 6.1 文生图流程

```text
1. 用户输入提示词并选择图片参数
2. 前端调用内容创作服务创建任务
3. 创作服务校验用户权限、额度和输入参数
4. Prompt 处理服务补全生成参数
5. 审核服务执行合规校验
6. 任务编排服务将任务投递到图片生成引擎
7. 图片生成引擎完成推理并返回结果
8. 后处理服务执行超分、格式转换等处理
9. 结果存入对象存储，元数据写入数据库
10. 前端通过轮询或 WebSocket 获取结果
```

### 6.2 文生视频流程

```text
1. 用户输入提示词、视频时长和风格参数
2. 内容创作服务创建视频任务
3. Prompt 处理服务标准化视频生成参数
4. 审核服务校验输入合规性
5. 编排服务将任务分发给视频生成引擎
6. 视频生成完成后进入后处理流程
7. 后处理服务执行转码、封面抽帧、压缩和格式适配
8. 视频文件与封面图写入对象存储
9. 作品元数据落库并通知前端结果可用
```

### 6.3 图生图 / 图生视频补充流程

相比文生类流程，增加以下环节：

- 用户上传参考图
- 素材管理服务完成存储与校验
- 创作任务引用参考图地址和元数据
- 编排层将参考图作为模型输入参数的一部分

## 7. 核心模块职责说明

### 7.1 为什么要单独建设内容创作服务

内容创作服务不直接承担推理职责，而是作为前台业务统一入口。这样设计有几个原因：

- 屏蔽前端对底层模型差异的感知
- 统一控制额度、风控、任务规则
- 便于后续扩展为 API 开放平台
- 降低前端和 AI 引擎之间的耦合

### 7.2 为什么要引入任务编排层

图片和视频生成耗时长、资源重，不能走简单同步接口。任务编排层的价值在于：

- 把同步请求转成异步任务
- 控制队列优先级
- 支持失败重试和任务恢复
- 记录任务全过程，便于审计和计费

### 7.3 为什么要区分图片引擎和视频引擎

图片和视频在资源消耗、时延、输入参数和后处理逻辑上差异很大，分开治理更合理：

- 图片任务更适合高并发短任务
- 视频任务更适合低并发长任务
- 两类任务的 GPU 规格和扩容策略不同
- 后续可以独立优化成本和性能

## 8. 技术架构建议

### 8.1 前端技术

- Web：React 或 Next.js
- 管理后台：React + Ant Design
- 实时任务通知：WebSocket 或 SSE

### 8.2 后端技术

- API 服务：FastAPI 或 NestJS
- 编排服务：建议 Python 技术栈，方便 AI 工作流整合
- 任务执行：Celery、Temporal 或 Argo Workflows
- 消息队列：Kafka 或 RabbitMQ
- 数据库：PostgreSQL
- 缓存：Redis
- 媒体处理：FFmpeg

### 8.3 模型接入策略

建议平台支持三种模型接入模式：

- 外部模型 API
- 自建推理服务
- 混合路由模式

第一阶段建议采用“外部模型 API + 自建编排平台”的方式快速上线。后续当任务量稳定、成本模型清晰后，再逐步引入自建 GPU 推理集群。

## 9. 部署架构建议

### 9.1 目标部署形态

建议采用容器化和 Kubernetes 部署，原因如下：

- 方便服务拆分和独立扩容
- 适合异步任务体系
- 便于 GPU 节点池管理
- 方便灰度发布和弹性伸缩

### 9.2 逻辑部署结构

```text
Internet
   |
[CDN + WAF]
   |
[公网负载均衡]
   |
[Kubernetes Ingress]
   |
+-------------------- 应用服务区 --------------------+
| 认证服务 / 用户服务 / 创作服务 / 作品服务 / 后台服务 |
+--------------------------------------------------+
   |
+-------------------- 平台中间件区 ------------------+
| PostgreSQL / Redis / MQ / 对象存储 / 配置中心      |
+--------------------------------------------------+
   |
+-------------------- AI 推理区 --------------------+
| 图片 GPU 节点池 / 视频 GPU 节点池 / 后处理节点池   |
+--------------------------------------------------+
   |
+-------------------- 运维观测区 --------------------+
| 日志 / 指标 / 告警 / 链路追踪 / 审计               |
+--------------------------------------------------+
```

### 9.3 网络分区建议

- 公网区：CDN、WAF、负载均衡
- 应用区：前后端业务服务
- 数据区：数据库、缓存、消息队列、对象存储
- AI 区：GPU 推理节点和媒体处理节点
- 运维区：日志、监控、堡垒机、审计系统

原则上：

- 数据区和 AI 区不直接暴露公网
- 应用区通过内网访问中间件和推理服务
- 关键访问行为需要审计日志

## 10. 接口与集成设计建议

### 10.1 对前端开放的核心接口

- `POST /api/create/image`
- `POST /api/create/video`
- `GET /api/tasks/{taskId}`
- `GET /api/works/{workId}`
- `POST /api/assets/upload-reference`

### 10.2 内部服务接口

- `POST /internal/prompt/enhance`
- `POST /internal/moderation/check`
- `POST /internal/orchestrator/submit`
- `POST /internal/model/image/generate`
- `POST /internal/model/video/generate`
- `POST /internal/postprocess/execute`

### 10.3 外部系统对接点

如平台需接入企业现有 IT 景观，建议优先复用以下系统：

- 企业统一身份认证系统
- 统一支付或计费系统
- 统一对象存储平台
- 企业消息通知平台
- 企业日志与监控平台
- 企业内容审核平台

## 11. 安全与合规要求

平台必须从设计初期考虑安全与合规，不应等到上线前补齐。

重点包括：

- 用户身份认证与权限控制
- 接口限流、防刷、防滥用
- 提示词审核
- 生成结果审核
- 文件上传安全检查
- 敏感数据脱敏与审计
- 下载地址权限控制和时效控制

如果面向企业客户，还应考虑：

- 租户隔离
- 数据分域存储
- 访问日志保留
- 私有化部署支持

## 12. 非功能需求

### 12.1 性能

- 图片生成请求高峰期需要支持高并发排队
- 视频生成任务需具备长任务稳定处理能力
- 前端需要清晰展示任务进度和状态

### 12.2 可用性

- 核心业务服务多副本部署
- 消息队列和数据库主从或高可用部署
- 任务失败可恢复，避免重复扣费

### 12.3 可扩展性

- 支持新增模型时不影响前端调用方式
- 支持新增创作模式，如海报、头像、短片模板
- 支持未来开放 API 给第三方调用

### 12.4 可观测性

建议重点监控以下指标：

- 任务提交量
- 排队时长
- 平均生成时长
- 成功率与失败率
- 单任务平均成本
- GPU 利用率
- 热门模型和热门风格分布

## 13. 分阶段建设建议

### 13.1 一期：MVP

目标：先跑通从提示词到结果交付的最小闭环。

范围建议：

- 用户登录
- 文生图
- 文生视频
- 异步任务管理
- 作品列表
- 基础审核
- 对象存储和结果下载

### 13.2 二期：能力增强

- 图生图
- 图生视频
- 模板中心
- Prompt 优化
- 会员与积分体系
- 分享发布

### 13.3 三期：平台化与企业化

- 多模型路由
- 团队协作
- 企业素材库
- 开放 API 平台
- 自建 GPU 推理集群
- 私有化或专有云部署能力

## 14. 结论

AI 内容创作平台本质上不是单一模型调用页面，而是一个围绕创作任务、模型编排、媒体处理、内容治理和运营体系构建的平台系统。

从架构上，应优先保证以下几点：

- 前台体验统一
- 后台任务异步可控
- 模型能力解耦可替换
- 媒体结果可管理可追踪
- 安全、审核、计费、监控从一开始纳入设计
