# AI内容创作平台微服务拆分说明

## 1. 文档目的

本文档基于《AI内容创作平台整体架构说明》，进一步细化平台的微服务拆分方案，用于指导后续系统设计、开发实施和部署规划。

本文档重点回答以下问题：

- 平台应该拆分为哪些核心服务
- 每个服务负责什么能力边界
- 服务之间如何调用和协作
- 哪些服务适合一期建设，哪些适合后续演进
- 如何避免前期过度拆分带来的复杂度

## 2. 拆分原则

微服务拆分不以“服务数量多”为目标，而以“职责边界清晰、可独立演进、可独立扩缩容”为目标。

本平台建议采用以下拆分原则：

- 按业务域拆分，而不是按表拆分
- 高耦合能力先聚合，低耦合能力再逐步独立
- 用户面向能力与 AI 推理能力分层
- 长耗时异步任务与同步接口处理分离
- 强状态数据与大文件媒体数据分离
- 频繁扩缩容的推理服务与稳定业务服务分离部署

## 3. 总体拆分思路

对于 AI 内容创作平台，不建议第一阶段就拆成十几个独立服务。更合理的方式是：

- 一期采用“核心业务服务 + AI 编排服务 + 推理服务 + 平台基础服务”的结构
- 二期随着业务量和团队规模增长，再拆出审核、计费、素材、通知等独立服务
- 三期形成支持多模型、多租户、开放 API 的平台化微服务体系

建议将服务分为四类：

- 接入与体验类服务
- 核心业务类服务
- AI 中台类服务
- 平台支撑类服务

## 4. 目标微服务清单

### 4.1 服务总览

| 服务名称 | 服务标识 | 主要职责 | 建议阶段 |
|---|---|---|---|
| API网关 | api-gateway | 统一入口、鉴权、限流、路由 | 一期 |
| 认证服务 | auth-service | 登录、注册、Token、SSO | 一期 |
| 用户与订阅服务 | user-billing-service | 用户资料、套餐、积分、额度、账单 | 一期 |
| 内容创作服务 | creation-service | 创建创作任务、参数校验、创作入口统一封装 | 一期 |
| 作品服务 | work-service | 作品列表、版本、下载、分享、删除 | 一期 |
| 素材服务 | asset-service | 参考图上传、素材元数据、素材复用 | 二期 |
| Prompt处理服务 | prompt-service | 提示词增强、模板拼接、参数标准化 | 一期 |
| 审核策略服务 | moderation-service | 提示词审核、结果审核、策略控制 | 一期 |
| 任务编排服务 | orchestration-service | 任务状态机、调度、回调、重试 | 一期 |
| 模型路由服务 | model-routing-service | 模型选择、策略分流、灰度路由 | 二期 |
| 图片生成服务 | image-generation-service | 图片类模型推理执行 | 一期 |
| 视频生成服务 | video-generation-service | 视频类模型推理执行 | 一期 |
| 后处理服务 | postprocess-service | 超分、转码、缩略图、封面、水印 | 一期 |
| 通知服务 | notification-service | 站内信、邮件、短信、任务完成通知 | 二期 |
| 管理后台服务 | admin-service | 运营配置、审核台、模型策略配置 | 一期 |
| 监控审计服务 | observability-audit | 日志、审计、指标、追踪 | 一期 |

说明：

- `observability-audit` 更多是平台能力集合，工程上未必是单个自研服务，也可以由日志、APM、审计系统共同承担。
- `model-routing-service` 在一期可以先内嵌在 `orchestration-service` 中，二期再独立。
- `asset-service` 在一期如果只做基础参考图上传，也可以先合并在 `work-service`。

## 5. 服务边界说明

### 5.1 API网关

职责：

- 作为所有外部请求统一入口
- 统一鉴权与权限透传
- 接口限流、防刷、防滥用
- 路由到后端对应服务
- 记录访问日志与请求链路标识

不负责：

- 业务规则判断
- 任务编排
- 模型调用

设计建议：

- 对外只暴露网关地址，不直接暴露内部服务
- 注入 `trace_id`、`user_id`、`tenant_id` 等上下文信息

### 5.2 认证服务

职责：

- 用户注册、登录、注销
- Access Token / Refresh Token 管理
- 第三方登录和企业 SSO 接入
- 设备登录态和风控基础校验

边界说明：

- 认证服务只负责“你是谁”
- 用户与订阅服务负责“你有什么权限、套餐和额度”

### 5.3 用户与订阅服务

职责：

- 用户档案
- 套餐定义与购买关系
- 积分、额度、会员权益
- 用量统计
- 扣费与消费记录

边界说明：

- 不负责支付渠道对接细节时，可先保留支付适配接口
- 后续如支付逻辑复杂，可再拆出计费服务和支付服务

### 5.4 内容创作服务

职责：

- 提供统一创作入口
- 接收图片和视频生成请求
- 校验请求参数完整性
- 校验用户是否有创作权限和可用额度
- 创建业务任务单并调用编排服务

边界说明：

- 该服务不直接调用底层模型
- 该服务负责面向前端的创作体验一致性
- 该服务负责把“业务请求”翻译成“平台任务”

这是平台的一号核心业务服务，建议不要过早拆散。

### 5.5 作品服务

职责：

- 保存作品元数据
- 管理作品与任务、用户之间的关联关系
- 提供作品列表、详情、删除、下载、分享
- 管理作品版本和再生成链路

边界说明：

- 作品服务管理的是“业务对象”
- 对象存储管理的是“媒体文件本体”
- 两者不能混淆

### 5.6 素材服务

职责：

- 上传参考图、品牌图、模板素材
- 素材分类和标签管理
- 素材元数据存储
- 为图生图和图生视频提供标准输入

边界说明：

- 一期若仅支持简单上传，可先并入作品服务
- 二期当素材复用、分类、审核需求增加后再独立

### 5.7 Prompt处理服务

职责：

- 提示词清洗
- 风格模板拼接
- 负面提示词补全
- 多语言转换
- 图片和视频参数标准化

边界说明：

- Prompt 服务负责“生成输入结构化”
- 不负责任务调度和推理执行

建议原因：

- 该能力演进频繁
- 可能引入模板库、风格词库、企业术语库
- 独立后更利于快速迭代

### 5.8 审核策略服务

职责：

- 提示词审核
- 生成结果审核
- 用户黑白名单
- 风险策略控制
- 按用户等级、区域或租户控制模型能力

边界说明：

- 审核策略服务是平台安全控制点
- 不应分散在各业务服务中重复实现

### 5.9 任务编排服务

职责：

- 创建任务执行单
- 维护任务生命周期状态
- 任务入队、分发、重试和取消
- 接收模型执行结果
- 驱动后处理流程

边界说明：

- 编排服务是平台二号核心服务
- 所有长任务必须纳入编排，不允许业务服务直连模型后长时间阻塞

建议采用状态机驱动，状态示例：

- `created`
- `queued`
- `running`
- `post_processing`
- `reviewing`
- `success`
- `failed`
- `cancelled`

### 5.10 模型路由服务

职责：

- 根据任务类型匹配模型
- 根据时延、成本、质量和套餐做策略分流
- 灰度发布新模型
- A/B Test

边界说明：

- 一期可先嵌入编排服务
- 二期当模型数量增加后再独立

是否独立的判断标准：

- 模型数超过 3 至 5 个
- 不同租户需要不同模型策略
- 需要精细化成本控制和实验能力

### 5.11 图片生成服务

职责：

- 执行文生图、图生图、局部重绘等图片任务
- 封装底层图片模型调用
- 回传推理状态与结果

边界说明：

- 对上只暴露统一图片生成接口
- 对下可以接外部 API，也可以接本地 GPU 推理实例

### 5.12 视频生成服务

职责：

- 执行文生视频、图生视频等视频任务
- 处理长任务回调和结果状态上报
- 对接视频模型供应方或自建推理集群

边界说明：

- 视频任务耗时长、成本高，必须独立部署
- 不应与图片生成服务共享相同扩容策略

### 5.13 后处理服务

职责：

- 图片超分和格式转换
- 视频转码和压缩
- 缩略图与封面生成
- 水印和输出标准化

边界说明：

- 后处理应与推理服务解耦
- 后处理失败不应直接导致任务上下文丢失

### 5.14 通知服务

职责：

- 任务完成通知
- 审核结果通知
- 订阅额度预警
- 站内信、邮件、短信、Webhook

边界说明：

- 一期可以先由业务服务直接发站内通知
- 二期后统一收敛为通知服务

### 5.15 管理后台服务

职责：

- 后台登录与权限
- 用户管理
- 内容审核工作台
- 模板和风格配置
- 模型策略、额度规则、运营参数管理

边界说明：

- 管理后台服务不是普通前端页面，它对应独立后台业务能力
- 不建议直接复用用户端接口拼后台逻辑

## 6. 服务调用关系

### 6.1 同步调用主链路

```text
前端
  -> API网关
    -> 认证服务
    -> 内容创作服务
      -> 用户与订阅服务
      -> Prompt处理服务
      -> 审核策略服务
      -> 任务编排服务
```

说明：

- 用户提交创作请求时，前半程应以同步校验为主
- 只要进入编排服务，就应转为异步处理

### 6.2 异步执行主链路

```text
任务编排服务
  -> 消息队列
    -> 图片生成服务 / 视频生成服务
      -> 后处理服务
        -> 对象存储
        -> 作品服务
        -> 审核策略服务
        -> 通知服务
```

说明：

- 推理执行和后处理尽量走异步事件流
- 作品服务只在结果稳定后更新最终可见状态

## 7. 建议的数据归属

微服务拆分必须配套数据归属边界，否则只是逻辑拆分，最终仍会回到共享库耦合。

建议的数据归属如下：

| 服务 | 主数据 |
|---|---|
| 认证服务 | 账号、凭证、登录态、SSO映射 |
| 用户与订阅服务 | 用户档案、套餐、积分、额度、消费记录 |
| 内容创作服务 | 创作请求单、创作参数快照 |
| 作品服务 | 作品、版本、分享记录、下载记录 |
| 素材服务 | 素材元数据、标签、引用关系 |
| Prompt处理服务 | 模板、风格词库、参数映射规则 |
| 审核策略服务 | 审核记录、策略规则、黑白名单 |
| 任务编排服务 | 任务单、任务状态、回调记录、重试记录 |
| 图片/视频生成服务 | 模型调用日志、执行结果缓存 |
| 后处理服务 | 转码记录、输出格式记录 |

设计要求：

- 每个服务拥有自己的逻辑主数据
- 不建议多个服务直接写同一张业务主表
- 跨服务取数优先通过接口或事件，而不是跨库直查

## 8. 服务拆分优先级

### 8.1 一期建议最小服务集

一期目标是尽快跑通业务闭环，因此建议控制服务数量。

建议一期部署为以下 8 个核心单元：

1. API网关
2. 认证服务
3. 用户与订阅服务
4. 内容创作服务
5. 作品服务
6. Prompt处理 + 审核策略 + 编排服务
7. 图片生成服务
8. 视频生成服务
9. 后处理服务
10. 管理后台服务

说明：

- `Prompt处理服务`、`审核策略服务`、`模型路由服务` 一期可先合并到编排服务域中
- `素材服务`、`通知服务` 可先不独立
- 数据库可先按服务域划分 schema，再逐步演进到完全独立库

### 8.2 二期建议独立的服务

当出现以下情况时，应开始进一步拆分：

- 用户量和任务量明显增长
- 审核策略频繁变化
- 模型供应商数量增加
- 企业租户开始接入
- 运营能力明显增强

二期建议独立：

- 素材服务
- 审核策略服务
- 模型路由服务
- 通知服务

### 8.3 三期平台化服务演进

三期面向企业化和开放平台，建议继续演进：

- 多租户管理服务
- 开放API管理服务
- 支付服务
- 结算服务
- 团队协作服务
- 企业配置中心

## 9. 部署建议

### 9.1 按资源特性分区部署

建议将微服务按资源特性划分部署区：

- 业务服务区：认证、用户、创作、作品、后台
- AI中台区：Prompt、审核、编排、模型路由
- 推理区：图片生成、视频生成
- 媒体处理区：后处理、转码
- 平台区：数据库、缓存、消息队列、对象存储

### 9.2 扩容策略建议

不同服务扩容方式不同：

| 服务类别 | 扩容重点 |
|---|---|
| API与业务服务 | 按QPS和CPU扩容 |
| 编排与审核服务 | 按任务数和消息积压扩容 |
| 图片生成服务 | 按GPU利用率和图片任务队列扩容 |
| 视频生成服务 | 按GPU利用率和视频任务队列扩容 |
| 后处理服务 | 按CPU、IO和转码队列扩容 |

架构上必须接受一个事实：视频服务和图片服务不能用同一套扩容参数治理。

## 10. 服务治理建议

为了避免微服务数量上升后系统失控，建议同步建设以下治理机制：

- 统一服务注册与发现
- 统一配置中心
- 统一日志规范
- 统一链路追踪
- 统一错误码体系
- 统一接口鉴权规范
- 统一事件命名规范
- 统一幂等控制机制

建议关键事件命名示例：

- `creation.task.created`
- `generation.image.completed`
- `generation.video.completed`
- `work.asset.published`
- `moderation.result.rejected`

## 11. 风险与控制点

### 11.1 过度拆分风险

常见错误是前期把每个概念都拆成服务，导致：

- 接口数量暴涨
- 调试链路过长
- 数据一致性复杂
- 小团队运维成本过高

控制建议：

- 一期先按业务域聚合
- 有明确扩展压力后再独立

### 11.2 共享数据库风险

如果多个服务共享同一组核心业务表，后续会出现：

- 服务边界失效
- 变更影响范围不可控
- 无法独立演进

控制建议：

- 至少先做 schema 隔离
- 再逐步走向逻辑独立库

### 11.3 推理服务阻塞业务链路风险

如果业务服务同步等待模型返回，会导致：

- 接口超时
- 前端体验差
- 服务线程耗尽

控制建议：

- 所有图片和视频生成都必须任务化
- 对前端只返回任务状态，不同步等待最终媒体结果

## 12. 推荐实施顺序

建议按以下顺序推进：

1. 确定一期服务边界
2. 输出核心服务 API 草案
3. 确定数据库归属和主表边界
4. 定义任务状态机和事件流
5. 确定消息队列主题和回调机制
6. 完成部署拓扑和容量预估

## 13. 结论

该平台的微服务拆分应围绕两个核心中心展开：

- 面向用户的创作业务中心
- 面向任务执行的 AI 编排中心

前者负责统一创作体验、作品管理和运营规则，后者负责把创作请求稳定地转成图片或视频结果。

在实施上，建议坚持两个原则：

- 一期先少拆，但边界要对
- 推理、编排、业务三层必须明确分开

下一步最合理的延续工作是：

1. 核心数据库设计
2. 核心接口设计
3. 任务状态机设计
