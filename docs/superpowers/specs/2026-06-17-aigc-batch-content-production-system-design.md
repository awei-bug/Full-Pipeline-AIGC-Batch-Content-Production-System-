# 全链路 AIGC 批量内容生产系统重构设计

## 1. 背景

当前仓库已经具备一个可运行的 AI 内容创作 MVP：

- `studio-web` 提供前端交互界面
- `api-server` 提供项目、任务、作品、资产管理接口
- `ai-orchestrator` 基于 FastAPI + LangGraph 承担生成编排

但现有业务主线仍然是“单次创作请求 -> 单任务生成 -> 返回图片/视频结果”。这条主线适合创作型演示，不适合面向商家、自媒体和运营团队的批量内容生产场景。

新的目标不是继续强化视频单点能力，而是将项目重构为一个面向商家和自媒体团队的 **全链路 AIGC 批量内容生产系统**，重点支持：

- 批量导入商品数据
- 批量生成文案、营销标题、短视频脚本、海报提示词
- 自动生成配图
- 批量导出内容成果
- 基础成本统计和内容安全风控

## 2. 新产品定位

### 2.1 目标用户

- 电商商家
- 品牌运营团队
- 自媒体内容团队
- 中小型代运营团队

### 2.2 核心价值

- 从“逐条手工写内容”切换为“按商品表批量出内容”
- 从“单次创作体验”切换为“任务式内容生产流水线”
- 从“单一模型调用”切换为“结构化数据 + 提示词模板 + 多模态生成 + 导出交付”

### 2.3 第一阶段主卖点

用户上传一份商品 Excel 或 CSV 后，系统可以自动生成：

- 商品卖点文案
- 商品营销标题
- 短视频口播脚本
- 商品图文描述
- 海报提示词
- 商品配图

最终支持结果列表查看、批量筛选和导出。

## 3. 重构目标

## 3.1 目标

在保留现有基础设施的前提下，重构业务层，使系统从“单任务创作站点”演进为“批量内容生产中台 MVP”。

### 3.2 保留部分

- 前端工程结构：`apps/studio-web`
- Node API 服务壳：`apps/api-server`
- Python 编排服务壳：`apps/ai-orchestrator`
- PostgreSQL 初始化脚本和本地联调脚本
- 作品和资产的基础持久化思路

### 3.3 重写部分

- 业务对象模型
- 前端主页面结构
- 批任务体系
- 编排主流程
- 导入/导出能力
- 内容模板体系
- 风控与成本统计链路

## 4. 非目标

本次重构第一阶段不追求以下能力完整上线：

- 企业级权限体系
- 正式计费结算
- 私有化大模型部署
- 自动 Prompt 自优化闭环全量落地
- 稳定的长视频成片生产
- 多智能体剧本工坊、角色设计、分镜工作流

这些能力会在架构上预留扩展位，但不作为第一阶段交付标准。

## 5. 推荐重构路线

推荐采用 **“保留基础设施，重写业务层”** 的方案。

原因：

1. 现有三服务结构已经能跑通，继续复用可以减少重建成本。
2. 当前“单次创作任务”的业务模型不适合批量生产，继续叠加会越来越乱。
3. 新目标更依赖批量数据处理、任务拆分和流水线状态管理，而不是单一模型能力。

## 6. 新系统核心业务流

第一阶段的主业务流定义为：

```text
导入商品数据
-> 字段映射与结构化存储
-> 创建批量生产任务
-> 按商品拆分子任务
-> 生成文案/标题/脚本/提示词
-> 生成配图
-> 风控审核
-> 汇总结果
-> 导出 Excel / 查看详情
```

这是新系统最关键的一条生产闭环，其他能力都围绕这条闭环展开。

## 7. 模块设计

### 7.1 数据接入中心

职责：

- 上传 Excel / CSV
- 自动解析表头
- 用户确认字段映射
- 将原始商品数据标准化为结构化记录

建议字段模型：

- 商品名称
- 商品卖点
- 商品分类
- 品牌
- 价格
- 规格参数
- 目标人群
- 使用场景
- 主图链接
- 附加描述

处理结果：

- 保留原始导入批次
- 生成标准化商品记录
- 保存字段映射配置，便于下次复用

### 7.2 商品数据存储层

新增的数据核心不是“作品”，而是“商品”和“导入批次”。

建议新增实体：

- `import_batches`
- `import_batch_fields`
- `products`
- `product_attributes`
- `content_jobs`
- `content_job_items`
- `content_outputs`
- `prompt_templates`
- `risk_events`
- `usage_metrics`

其中：

- `import_batches` 记录一次导入
- `products` 记录标准化商品
- `content_jobs` 记录一次批量生产任务
- `content_job_items` 记录每个商品的子任务
- `content_outputs` 记录最终生成成果

### 7.3 模板与策略中心

职责：

- 管理不同内容类型的模板
- 管理不同渠道和风格的 Prompt 结构
- 将商品数据填入模板，形成结构化生成请求

第一阶段模板建议支持：

- 商品卖点文案模板
- 营销标题模板
- 短视频脚本模板
- 图像提示词模板
- 海报提示词模板

模板设计原则：

- 模板与生成任务解耦
- 支持版本化
- 支持按渠道区分
- 支持后续评测反馈回写

### 7.4 批量生产引擎

职责：

- 创建批量任务
- 将任务按商品拆分为子任务
- 控制并发、重试、超时
- 汇总各阶段结果

任务状态建议：

- `created`
- `queued`
- `running`
- `partial_success`
- `success`
- `failed`
- `cancelled`

子任务状态建议：

- `pending`
- `running`
- `copy_ready`
- `image_ready`
- `risk_blocked`
- `success`
- `failed`

### 7.5 多模态生成流水线

第一阶段流水线建议如下：

```text
商品结构化数据
-> 文案生成
-> 脚本生成
-> 图像提示词生成
-> 图像生成
-> 结果标准化
-> 资产保存
```

说明：

- 长视频生成不作为第一阶段主链路
- 图像生成优先保留现有魔塔路径
- 视频脚本是“文本输出物”，不强依赖视频模型

### 7.6 Text2SQL 与结构化查询模块

Text2SQL 是这次需求中的亮点，但不应作为第一阶段主入口。

第一阶段建议：

- 先提供结构化字段映射和标准化商品表
- 编排器直接读取结构化商品数据构造 Prompt

第二阶段再扩展：

- Agent 根据用户意图生成 SQL
- 面向 PostgreSQL 商品库做动态查询
- 用 SQL 查询结果补充 Prompt 上下文

这样可以避免一开始就把复杂性压到查询层。

### 7.7 Prompt 优化与评测模块

第一阶段只做“可接入的基础版”：

- 模板版本管理
- 人工评分记录
- 内容结果回看

第二阶段再扩展：

- BLEU / ROUGE 自动评测
- 模板对比实验
- 基于历史表现的 Prompt 迭代推荐

原因：

- 商业内容生成更依赖人工业务判断
- 纯文本指标对营销内容质量代表性有限
- 第一阶段更需要先建立数据闭环和评测存档能力

### 7.8 并发与成本控制模块

第一阶段必须具备基础统计，不然系统无法运营。

建议第一阶段支持：

- 每个批任务的生成数量统计
- 每个内容类型的调用次数统计
- 每个任务的 token 估算或 provider 调用成本记录
- 并发上限配置
- 子任务失败重试上限

第二阶段再扩展：

- Embedding 缓存
- Prompt 去重缓存
- vLLM / Ollama 本地推理接入
- 多 provider 动态路由和成本调度

### 7.9 内容安全风控模块

第一阶段必须上线基础风控。

建议采用双层机制：

1. 规则层
   - 敏感词检测
   - 违规行业词库
   - 黑名单主题过滤

2. 模型审核层
   - 对生成文本做二次审核
   - 对图像提示词做安全检查

结果处理：

- 违规子任务标记为 `risk_blocked`
- 记录风险事件日志
- 提供前端查看和人工处理入口

## 8. 系统架构

### 8.1 前端 `studio-web`

新首页不再是单个提示词生成器，而应改为生产工作台，至少包含：

- 导入批次列表
- 商品列表
- 批量生产任务列表
- 任务详情页
- 结果预览页
- 模板管理页
- 风控日志页

第一阶段可以先只做：

- 导入页
- 任务页
- 结果页

### 8.2 API 服务 `api-server`

建议成为业务主服务，负责：

- 商品导入接口
- 字段映射接口
- 批量任务创建接口
- 任务/子任务查询接口
- 结果导出接口
- 风控日志查询接口
- 成本统计查询接口

现有项目、作品、资产接口可以保留，但要为新业务模型服务。

### 8.3 编排服务 `ai-orchestrator`

建议成为生产流水线引擎，负责：

- 接收批任务分发
- 为每个商品执行内容生成流水线
- 与不同 provider 交互
- 回写结果和阶段状态

编排粒度要从“单个创作请求”升级为“批任务项”。

### 8.4 数据库

建议继续以 PostgreSQL 为主存储。

原因：

- 结构化商品数据适合关系型存储
- 后续 Text2SQL 直接复用 PostgreSQL
- 批任务、风控日志、成本统计也适合结构化管理

## 9. 数据流设计

### 9.1 导入流

```text
前端上传 Excel
-> api-server 解析文件
-> 返回字段样本与表头
-> 用户确认字段映射
-> api-server 写入 import_batches / products
```

### 9.2 批量生成流

```text
前端创建内容任务
-> api-server 创建 content_job 和 content_job_items
-> ai-orchestrator 拉起子任务
-> 逐条执行生成流水线
-> 回写 content_outputs / assets / task status
```

### 9.3 导出流

```text
用户发起导出
-> api-server 查询 content_outputs
-> 组装导出 Excel
-> 返回下载地址
```

## 10. 错误处理设计

第一阶段错误处理原则：

- 单个商品失败不应拖垮整个批任务
- 批任务允许部分成功
- 每个子任务必须记录失败原因

错误分类建议：

- `IMPORT_PARSE_FAILED`
- `FIELD_MAPPING_INVALID`
- `PROMPT_BUILD_FAILED`
- `TEXT_GENERATION_FAILED`
- `IMAGE_PROMPT_FAILED`
- `IMAGE_GENERATION_FAILED`
- `RISK_BLOCKED`
- `EXPORT_FAILED`

## 11. 测试策略

第一阶段测试重点不是 UI 细节，而是生产链路正确性。

### 11.1 API 测试

- 导入接口
- 字段映射接口
- 批任务创建接口
- 结果查询与导出接口

### 11.2 编排测试

- 单个商品内容流水线成功
- 部分商品失败时批任务状态正确
- 风控拦截逻辑正确
- 图像生成结果能正常落盘和回写

### 11.3 前端测试

- 导入流程
- 批量任务状态展示
- 结果列表展示
- 导出入口

## 12. 第一阶段交付范围

第一阶段交付完成的标准定义为：

1. 用户可以上传商品 Excel / CSV
2. 用户可以映射字段并保存商品数据
3. 用户可以发起批量内容生成任务
4. 系统可以为每个商品生成：
   - 标题
   - 卖点文案
   - 短视频脚本
   - 图像提示词
   - 配图
5. 用户可以查看结果列表
6. 用户可以导出 Excel
7. 系统具备基础风控和调用统计

## 13. 第二阶段扩展位

为后续迭代预留以下扩展位：

- Text2SQL 查询代理
- Prompt 自动评测与模板优化
- Embedding 缓存
- 多 provider 路由
- 本地模型私有化推理
- 更复杂的多模态排版输出
- 账号体系与配额计费

## 14. 风险与控制

主要风险：

1. 继续沿用旧的“单创作请求”业务模型会造成结构混乱
2. 一次性塞入 Text2SQL、Prompt 优化、私有化推理会让第一阶段失控
3. 图像与脚本之外的复杂视频生产会拖慢整体落地

控制方式：

1. 第一阶段只围绕批量内容生产闭环
2. Text2SQL 和 Prompt 自动优化作为第二阶段扩展
3. 视频部分在第一阶段只保留脚本文本，不强依赖视频模型

## 15. 结论

当前最合理的重构方向是：

- 保留现有三服务基础设施
- 重写业务层为“商品数据 -> 批量内容生产”的模型
- 用批任务与子任务替代旧的单创作任务
- 以文案、脚本、图像提示词、配图、导出为第一阶段主线
- 将 Text2SQL、Prompt 优化、私有化推理作为后续增强能力

这条路线的优点是：

- 能最快形成新的可演示产品闭环
- 能真实服务商家和内容团队场景
- 能为后续企业级扩展留下清晰接口和数据模型
